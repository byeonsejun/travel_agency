## 0. 컨텍스트 — 백엔드 계약 (변경 금지, 호출만)

이 계획은 **이미 구현된 백엔드 위에 프론트 E2E 플로우만 입힌다.** 아래 계약을 신뢰하고 호출한다.

| 자산 | 위치(barrel) | 시그니처 / 비고 |
|---|---|---|
| `createBooking` | `@/entities/booking` | `(CreateBookingInput) → Booking`. 좌석 CAS 차감 + travelers + terms + event를 단일 Tx. 가격 서버 재계산(`expectedTotalPrice` 불일치 시 throw). 생성 상태 = `RECEIVED`. |
| `transitionStatus` | `@/entities/booking` | `assertTransition` 통과 후 상태 전이 + `BookingEvent` append. |
| `getBookingDetail` | `@/entities/booking` | `(id, userId)` — **userId 스코프 조회**(소유권 = 쿼리 경계). travelers/terms/payments/events/departure 포함. |
| `buildOrderId` | `@/entities/payment` | `(bookingId, seq≥1) → "${bookingId}__${seq}"`. Toss 멱등 키. |
| `POST /api/payments/confirm` | route | body `{ paymentKey, orderId, amount:int }`. 멱등(orderId UNIQUE). 결과 `{ bookingId, status:"PAID"|"FAILED", failureMessage? }`. `confirmPayment`는 `booking.status === "DEPARTURE_CONFIRMED"`만 결제 허용. |
| `getDeparturesByProduct` | `@/entities/departure` | PDP·체크아웃 요약용 출발일(priceAdult/Child 포함). |

### 0.1 핵심 설계 결정 (Domain Booking 승인 필요)

- **D1. 상태 갭 처리**: `createBooking` → `RECEIVED`. 그러나 `confirmPayment`는 `DEPARTURE_CONFIRMED`만 허용. MVP는 그룹 형성(AWAITING_GROUP) 비범위이므로, 체크아웃 Server Action이 booking 생성 직후 **서버에서** `transitionStatus(RECEIVED → DEPARTURE_CONFIRMED, actor:"system:checkout")`로 전이시켜 결제 가능 상태로 만든다. (`ALLOWED_TRANSITIONS.RECEIVED`에 `DEPARTURE_CONFIRMED` 포함 — 검증됨.)
- **D2. clientKey 전달**: `env.TOSS_CLIENT_KEY`는 `NEXT_PUBLIC_` 접두사 없음. RSC(서버)에서 `env.TOSS_CLIENT_KEY`를 읽어 `'use client'` 결제 위젯에 **prop으로 주입**(env.ts 변경 불필요, FSD 경계 유지). 미설정 시 `env.NODE_ENV !== "production"`에서만 토스 공개 테스트 키로 폴백(메모리: dev 폴백은 NODE_ENV 단일 기준).
- **D3. orderId seq**: 재시도 시 seq를 증가시켜야 중복 orderId(PG 409)를 회피. Server Action이 해당 booking의 기존 payment 수 + 1을 seq로 계산해 `buildOrderId` 호출, orderId를 클라이언트에 반환.
- **D4. confirm 호출 위치**: 토스 redirect(`successUrl`)는 GET. 승인은 인증 쿠키가 필요한 POST. 따라서 `/bookings/[id]/success`(RSC)가 `<ConfirmPayment>`(client)를 렌더 → 1회 POST `/api/payments/confirm`. 멱등 보장(orderId UNIQUE)이므로 중복 POST 안전, 그래도 client 측 single-flight ref로 이중 호출 차단.
- **D5. 소유권 경계**: 모든 `/bookings/*` 페이지는 `auth()` 가드 + `getBookingDetail(id, session.user.id)`(userId 스코프). 타인 booking은 쿼리에서 `null` → `notFound()`.
